## Current interface versus the older Figma mock

The [Figma wrapper](https://www.figma.com/design/C1zOM5qj4LF3YOd5NMCN8G?node-id=4-2406) contains [Launch `4:2410`](https://www.figma.com/design/C1zOM5qj4LF3YOd5NMCN8G?node-id=4-2410) and [Equipment setup `4:2572`](https://www.figma.com/design/C1zOM5qj4LF3YOd5NMCN8G?node-id=4-2572). Both are 390 logical units wide. The fresh read found 227 descendants, 73 text layers and 32 action/input instances, with none smaller than 44 logical units in either dimension. Text uses Roboto. The mock remains a prior design concept: it does not include the current carrier calculator, separate TX frequencies/reference fields, installed-control selector, or conventional GS7K practice. Its missing-manual card also does not represent the current registry. No mock was changed or treated as a current release screenshot.

The implemented CSS has a later **50 px minimum** for ordinary inputs/selects/textareas, overriding the earlier 43 px rule; buttons/file labels have 48 px minimums. Equipment setup buttons/selects explicitly use at least 44 px. Small checkbox glyphs sit inside larger label targets. Hidden file inputs are activated through their visible file label; the hidden input is not the advertised touch target. These are source dimensions, not fresh computed mobile measurements.

The new carrier inputs use visible enclosing labels (**Available low/high carrier (MHz)**), `step="any"`, explicit 54–860 MHz bounds, and a labeled interpolation selector. Results show dBmV, MHz, high-minus-low dB and the selected curve. Example buttons identify themselves as filling a draft. Empty or out-of-range values produce explanatory status text rather than a fabricated zero. The local profile preset and calculated carrier draft stay distinct from the current launch readings. The TX-reference field has a separate frequency/service-plan field and explicitly distinguishes the transmitter plane from receive and injection settings. The focused GS7K job is separate from the complete AOI, OEM AGC and DSIM choices; synthetic state remains explicit.

Dark palette source contrasts on `--paper` are: ink 13.31:1, muted 8.72:1, blue 9.01:1, warn 8.99:1. These calculated text/background pairs do not certify every component, interaction state, browser font rendering or outdoor readability. Responsive grid/wrapping rules exist, and labels have `min-width:0`; this audit did not obtain a fresh narrow rendered layout.

## Platform API contract checks

| Path | Source finding and practical limit |
| --- | --- |
| File chooser/import | `evidence-ui.js` reads selected `FileList` entries on `change`, copies the list before clearing the input, and reads original bytes with `arrayBuffer()`. Project import reads `File.text()` and validates before loading. The file chooser is implemented; no evidence drop-zone handler was found. MDN drag/drop guidance therefore is a capability boundary, not a tested feature. A chooser filter would only be a hint, not validation. |
| Download/share | `browser-files.js` creates a Blob/File, checks sharing support, and offers a fresh user action when preparation outlives activation. `navigator.share()` runs before another await. The download uses an object URL and revokes it later, also cleaning up on errors. It correctly says a download was requested and asks the user to confirm the destination. A click is not proof of an OS save. |
| Clipboard | `equipment-setup.js` calls `writeText()` from the copy action, awaits success, catches unsupported/denied access, and selects the exact code for the device Copy command. It checks the current job/station before updating delayed status. HTTPS, browser permissions and activation rules can still prevent direct copying. |
| Storage | Autosave catches storage failures; the new carrier/preset paths distinguish retained in-memory edits from a successful device save and recommend immediate export on failure. Named jobs and raw local files still depend on their browser/origin. `file:` localStorage behavior is not guaranteed; private browsing, storage policy and quota remain limitations. Persistent-storage requests are optional and do not replace backups. |
| Offline/update | The worker saves and verifies the cache during install, checks readiness before activation, claims clients, and removes old public caches only after readiness. The page requires a controller plus a positive worker response before saying offline-ready. `navigator.onLine` affects wording only. HTTPS/support are checked; an update asks for backup/reload and does not automatically reload the working job. First load, failed caching or an uncontrolled client cannot be assumed offline-ready. |
